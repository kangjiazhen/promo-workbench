# 房源宣传片独立模块设计 v2.1 —— 批量工作台

日期：2026-10-27（v2 当日，吸收 3 份构建方评审 + 4 项用户决策后修订为 v2.1）
状态：设计评审稿，尚未开始实现（等待用户批准）
替代：`docs/superpowers/specs/2026-10-26-property-promo-module-design.md`（v1）
模块名：`property_promo`

## 0. v2 相对 v1 的变化（只列改动）

| 项 | v1（2026-10-26） | v2（本稿） |
|---|---|---|
| 批量 | 一次上传一套房源 | **一次添加多个房源文件夹或一个父文件夹**，逐套识别 |
| 页面 | 四页线性流（上传→选片→设置→结果） | **任务列表工作台**：批量上传入口 + 任务列表 + 详情面板 + 全局设置抽屉 |
| 渲染触发 | 每套走完四页后生成 | **人工确认后渲染**：勾选多套 → 一键「批量生成」；未勾选不动 |
| 渲染执行 | 单个后台任务 | **并发工作池**（默认 2 并发，可调） |
| 上传 | 逐文件串行 | **并行上传**（全局并发预算，默认 4） |
| 设置 | 每套独立设置 | **全局默认 + 单套可覆盖** |

v1 其余契约不变并在本稿中自包含重述（§4）。

## 1. 用户真正要的东西

用户是批量制作房源宣传片的从业者：一次准备几套~十套房源照片（已按房间整理好文件夹），希望一次上传、逐套确认、批量出片，渲染不阻塞后续操作。

输入结构：

```text
批量添加的房源文件夹（或一个父文件夹下的多个子文件夹）
├── 房源A/
│   ├── 客厅/01.jpg, 02.jpg
│   ├── 主卧/01.jpg
│   └── 卫生间/01.jpg
├── 房源B/
│   └── …
```

- 每个被添加的一级文件夹 = 一套房源（父文件夹模式见 §3.1）。
- 房源内一级子文件夹名 = 房间名；其中的图片 = 该房间照片。
- 房间归属以文件夹为准，不用 AI 猜房间。
- 跨房间同名文件合法；跨房源同名房间/文件同样合法，房源之间完全隔离。
- 输出是每套一条可预览、下载、重新生成的宣传片。

## 2. 本版边界

### 包含

- 浏览器添加**多个房源文件夹**（拖拽多文件夹）或**一个父文件夹**（选择器单选目录，子文件夹自动拆套），可反复「继续添加」。
- 上传前逐套本地预检：房间数/照片数/结构问题。
- 任务列表工作台：逐套状态徽章、详情面板（照片墙、自动选片、手动换图排序、单套设置覆盖）。
- 全局默认设置（联系人/画幅/音乐）+ 单套覆盖。
- **人工确认后渲染**：勾选多套 →「批量生成」。
- 并发渲染工作池（默认 2 并发）与并行上传。
- 成片列表：预览、下载、失败重试、重新生成（版本化）。

### 明确不包含

- 不做上百套/天的目录监听自动流水线（本期小批量：几套~十套/次）。
- 不支持把照片散放在房源根目录；不自动编造面积、价格、户型、地址、卖点。
- 不做复杂视频时间轴编辑；不做手机微信内置浏览器文件夹上传承诺。
- 不依赖付费 AI 接口；不继续扩张旧的 `tools/promo_ui.py` 页面。

## 3. 批量上传

### 3.1 添加方式与分类规则（v2.1 钉死）

浏览器提供两种添加入口，**都**逐文件夹记录「添加方式」元数据：

1. **选择器**：`<input type="file" webkitdirectory>`（Chrome/Edge 中只能选中**一个**目录，`multiple` 对目录无效——不承诺多选）。选中目录按 §3.1 分类规则处理。
2. **拖拽**：把一个或多个文件夹拖入上传区，用 `DataTransferItem.webkitGetAsEntry()` 递归读取目录树。多文件夹拖入 = 每个文件夹独立走分类规则。拖拽能看到空目录（可用于空房源提示），选择器看不到（浏览器限制，见 §3.4）。

**分类规则（逐个被添加的文件夹，按图片所在深度判定）**：
- 有图片在**第二层**（`房间/图片.jpg`）→ 该文件夹是**房源根**（其子文件夹=房间）。用户真实结构就是这样：房源根目录里没有图片。
- 图片都在**第三层及以下**（`房源/房间/图片.jpg`）→ 该文件夹是**父文件夹**，每个含图片的子文件夹识别为一套房源。
- 两层都有图片 → 标红错误：`「客厅」里直接就有图片，而「厨房」里还有一层文件夹，分不清哪一层是房间`，并给出整理动作。
- 只有根层散图（`图片.jpg` 直接放在被添加文件夹里）→ 识别为房源，根散图按结构违规标红阻止。
- 父文件夹之下不再递归拆第三层：房间内的孙子文件夹按 §4 嵌套规则报错。

> 2026-10-28 修正：原规则写的是「直接子级含图片 → 房源根」，实测会把完全合规的 `房源/房间/图片` 识别成父文件夹并拆成 N 套（每个房间一套）。判据必须是**图片深度**；这条缺陷只有真浏览器端到端测试（`tests/e2e_browser.py`）才抓得到。

**父目录段在客户端剥离**：服务端契约保持 v1 的三段相对路径 `房源名/房间名/文件名`；父文件夹段（`父目录/`）在浏览器端拆套时剥掉，不传服务端，无需服务端改造。上传时每套单独 `POST /api/listings`（带 `rootDirName`），与 stage-① 契约一致。

**批次**：一次会话 = 一个批次对象（组织用，便于整批取消/续传）。批次在用户点「完成上传」进入工作台时关闭；「继续添加」只对未关闭的批次生效。关闭后想加新套 = 开新批次，与已有房源同列显示。

### 3.2 预检（浏览器本地，添加后立即显示）

每套一张卡片：`房源A · 6 个房间 · 38 张照片 · 12.4 MB`，以及：

- **红色（结构违规，阻止该套上传）**：根目录散图（`房源B 有 3 张图直接放在根目录，请移入房间子文件夹`）、房间下再嵌套（`房源A「客厅/实拍/」多嵌套一层，请把图片直接放进「客厅」`）。
- **黄色（警告，不阻止）**：不支持格式的文件（`2 个 .txt 文件将忽略`）。
- 拖拽添加时可见的**空房源**（文件夹下没有任何图片）→ 灰卡说明；选择器添加时空房源不可见（浏览器不上传空文件夹，属已知限制，文案说明）。
- **坏套标红但不阻塞整批**：好套可正常上传，坏套留在上传区待用户整理后重加。

预检与服务的结构校验共享同一份常量（支持格式、目录深度规则）——常量定义在一份共享文件，前端打包引用、后端 import 引用，避免两套口径（v2.1 钉死）。

### 3.3 上传执行

- 每套房源独立创建（`POST /api/listings`，逐套一次），套内文件并行上传。
- **全局上传并发预算 = 4**（唯一旋钮，多套同时上传共享预算；不区分每套/整批两个口径，v2.1 钉死）。
- 进度逐套显示（done/total、当前文件、失败列表）；支持取消单套或整批。
- 失败文件统一重试：每文件最多 3 次（退避 1s/2s/4s），不重传已成功文件。
- **续传键 = (listing_id, 三段相对路径, 字节数)**：重选同一文件夹续传时，服务端按此键跳过已存在文件。跨房间同名合法因为相对路径含房间名；同路径同字节数但内容不同的极端情况不处理（文档化限制，我的判断）。
- 服务端核对相对路径、文件数、字节数后，该套标记「上传完成」。

### 3.4 浏览器限制

- 空文件夹不出现在上传清单 → 空房间自动隐藏，不是错误；空房源仅拖拽模式可见（灰卡），选择器模式不可见。
- 选中祖父级目录（如整个盘/下载目录）导致拆出 0 套或全是空子目录 → 明确提示 `未发现房源文件夹，请选择包含多套房源的父文件夹`，且客户端预检扫描文件数上限 20,000（超出则提示选择更具体的目录，防止前端卡死）。
- 关闭页签前提示未完成上传；未完成的套显示「继续上传」，重选同一文件夹续传（按 §3.3 续传键）。

## 4. 输入规则与异常反馈（自包含，替代 v1 引用）

- 标准结构：`房源根/房间/图片`，正好三段。JPG/JPEG/PNG/WebP。
- 房间名支持中文、数字、字母；未知房间名保留，排在已知房间之后（客厅/客餐厅/主卧/次卧/卧室/书房/厨房/餐厅/卫生间/阳台/其他 为已知序，沿用已验证排序）。
- 三段以内的（根散图）、三段以上的（房间内嵌套）→ 该套红色阻止，错误信息指明套、文件、修复动作。
- 不支持的扩展名 → 黄色警告、列名、将忽略。
- 相对路径含 `..`、绝对路径、盘符、非法字符 → 拒绝并报错（防路径穿越）。
- 跨房间同名文件合法；跨房源同名合法，房源间完全隔离。
- 视频与界面均不出现房源地址或本机磁盘路径；不编造事实性信息。

## 5. 工作台设计（核心页面）

单页应用，三常驻区 + 一抽屉：

```text
┌──────────────────────────────────────────────────────┐
│ 顶栏：批量上传 │ 全局设置抽屉按钮 │ 渲染队列状态      │
├──────────────────────┬───────────────────────────────┤
│ 任务列表（左列）       │ 详情面板（右侧）               │
│ ☐ 房源A  [待确认]     │  房源A · 6 房间 · 已选 14 张   │
│ ☑ 房源B  [待确认]     │  ── 照片墙（按房间分组）       │
│ ☐ 房源C  [上传中 45%] │  自动选片标记 + 手动换图/排序  │
│ ☐ 房源D  [渲染中 60%] │  ── 单套设置覆盖               │
│ ☐ 房源E  [完成 ✓]     │  [生成本套]                    │
├──────────────────────┴───────────────────────────────┤
│ 底栏：已勾选 2 套 · [批量生成] · 渲染池 2/2 忙          │
└──────────────────────────────────────────────────────┘
```

### 5.1 任务列表（左列）

- 每行：勾选框、房源显示名（默认根文件夹名，可改）、状态徽章、照片计数。
- 状态机：`待上传 → 上传中(x%) → 待确认 → 排队渲染 → 渲染中(x%) → 完成 / 失败`。
  - 转换规则：`待确认` 是唯一能进入 `排队渲染` 的状态（渲染前必须人工确认）；`完成` 的套可再次勾选生成新版本（重新进入 `排队渲染`，历史版本保留）；`失败` 一键重试（照片与设置保留，回到 `排队渲染`）。
- 排序：新上传在前；失败置顶可选；支持按状态筛选。

### 5.2 详情面板（右侧）

- 上传完成后进入「待确认」，展示自动选片：`已选 14 张 · 预计约 50 秒`（时长公式见 §5.5）。
- 照片墙按房间分组；房间显示名可改；房间顺序拖动；房间折叠/展开。
- 照片保留/排除、拖动排序、放大预览；`模糊/过暗/重复` 标记给可理解文案，不显示模型内部分数。
- 人工调整不会被自动推荐覆盖。
- 房间名既是素材分组，也可以**印在画面上**（v2.1 后续修订）：**每一张**照片左下角都印它所属的房间名（brass 竖线 + 浅色字，字号按画布宽等比缩放）；名字取上传时的文件夹名，可在照片墙就地改。
  - 2026-10-29 用户钉死「每一张都要有房间标识」：从「每间第一张印一次」改为「每张都印」。渲染器据此让标签跨镜头稳定——同一房间连着的几张不重播淡入（否则每 2~3 秒闪一下像故障），只有房间名真的变了才淡入。
  - 标签在**生成时刻冻结**进 Storyboard（`shot.room_label`），渲染器只照着画；生成后再改名不影响已有成片，与 §6「生成即冻结」一致。
  - 可关：全局设置 `room_labels`（默认开）+ 单套覆盖（跟随全局 / 印 / 不印）。客户不想暴露户型时能整体关掉。
  - 仍然禁止：地址、本机路径绝不上画面（§4）。房间名是用户自己写的房间标签，不是房源地址。
- 单套设置覆盖区：联系人、画幅、音乐（无/内置合成/自定义上传）。「恢复全局默认」一键回退。
  - **画幅选项（v2.1 用户钉死：4:3 与 16:9 必须有，可更多）**：
    - 16:9 横版（1920×1080）
    - 9:16 竖版（1080×1920）
    - 4:3 横版（1440×1080）
    - 3:4 竖版（1080×1440）
    - 1:1 方形（1080×1080）
  - 一次生成选定一个画幅（用户钉死）；要多个画幅就多次生成，各占一个渲染任务、各自成版本。
- 底部 `生成本套` = 勾选该套并立即批量生成的快捷入口。
- **本套渲染中**：详情面板仍可编辑，但顶部提示 `渲染中，修改将在下次生成时生效`（渲染使用冻结的 Storyboard，见 §6）。

### 5.3 全局设置抽屉

- 联系人（姓名/电话/微信/机构/结语/二维码图）保存为默认，新上传的套自动继承用于展示。
- 全局画幅与音乐默认；全局渲染并发数（默认 2）与上传并发数（默认 4）；是否在画面印房间名（`room_labels`，默认开）。
- **生效时机（钉死）**：全局默认在上传时给新套做初始值；**真正渲染取值在点击「批量生成/生成本套」那一刻冻结**进 Storyboard。之后改全局不影响已排队/渲染中的套；未确认的套显示值在下次进入详情时刷新。

### 5.4 渲染队列

- 队列是**活视图**：只显示排队/渲染中（含进度、取消），没有活任务时整块收起；完成/失败的结果回到左侧任务列表与详情面板（成片版本、失败原因、重试入口）。
- 并发池：同时 N 套渲染（默认 2），其余排队。
- 每个渲染作业独立临时目录与输出目录；进度来自 Remotion 渲染回调写入 DB，前端 1s 轮询 `GET /api/render-jobs`（SSE 留待后续版本）。
- 完成的视频内嵌预览、`下载 MP4`、`打开所在文件夹`（本地应用，后端 `os.startfile` 打开输出目录）、`重新生成`（新版本）。
- 版本保留：每套保留最近 20 个版本，更旧自动清理（我的判断）。
- 刷新/重开页面：全部状态从 SQLite 恢复。**服务端重启**：启动时清扫——渲染中的作业标记 `失败（原因：服务器中断）`，清理孤儿进程残留的临时目录与半成品文件，用户一键重试（不自动重排队，行为可预期；我的判断）。
- **取消**：排队中的作业可取消（出队回 `待确认`）；渲染中的作业可取消（终止子进程+清理临时文件，标记 `已取消`，可再次排队）。`POST /api/render-jobs/{id}/cancel`。

### 5.5 视频时长公式（钉死，来自已验证旧栈参数）

`总时长 = 片头 4.2s + Σ(每张选中照片 2.4~3.2s，按镜头与运镜微调) + 片尾 5.6s`。14 张选中照片约 50s；对应旧栈 v10 实测 55.06s/17 镜头，参数已验证。

## 6. 人工确认后渲染（v2 核心流程）

```text
批量上传 → 每套自动选片 → 逐套人工确认（看图/调整/覆盖设置）
→ 勾选要出片的套 → 点「批量生成」→ 进入并发渲染队列
```

- 确认即勾选：勾选的套点「批量生成」后排队；未勾选的保持「待确认」不渲染。
- 渲染中允许继续上传、编辑其他套；编辑渲染中的本套按 §5.2 生效于下次生成。
- 每套渲染前冻结 Storyboard（镜头顺序/文案/画幅/运镜/音频/联系方式，含取值时刻），版本化保存；`批量生成` 幂等（重复点击不重复排队：已排队/渲染中的套跳过）。

## 6.5 复用已验证能力

- 选片、房间排序、重复检测、EXIF/质量标记：参考旧 `tools/property_promo.py` 已验证算法，按新契约重写迁入，不 import 旧模块。
- 渲染沿用 Remotion 机制（props 驱动 Film、逐镜头运镜），组件契约独立于旧 `remotion-composer/projects/listing-promo`。
- 质检沿用「渲染后 ffprobe + 抽帧 + 音画核对」与快照审阅图模式。
- **合成工程缓存的两个静默失败**（实测踩到，已修）：①渲染进程被强杀会留下 `.active-<pid>` 标记，若把死标记当成「另一路渲染在跑」，之后每次渲染都沿用旧构建——改了合成代码却出一样的片子，日志只说一句「另一路渲染正在运行」；归属必须按 pid 判活（`process.kill(pid, 0)`），新鲜度按源码 stamp 比对。②抢锁失败后不能直接沿用旧包，要先复查对方是否刚写入新 stamp。逻辑集中在 `renderer/bundle-cache.mjs`，由 `tests/test_bundle_cache.py` 守住。
- **并发渲染风险前置**：双作业并发 Remotion（各起 Node+Chromium）是本期最大技术风险。阶段①就做并发尖刺测试（两作业同时渲染到完成、独立临时目录、进度互不串扰），若机器扛不住则默认并发退到 1 并在 UI 说明（配置仍可调高）。

## 10. 实施顺序（v2.1 调整）

1. **工作台骨架 + 批量上传**：拖拽/选择器双入口、分类规则、预检、并行上传、批次、任务列表；**含垂直切片**——一套从上传到「桩渲染」（直接产出一个占位视频文件走完 job/版本/恢复全链路）再到刷新恢复，先把 SQLite 作业/版本 schema 与恢复语义钉死。**并发渲染尖刺**（两作业同渲染）在本阶段末验证。
2. **选片与设置**：详情面板、自动推荐、人工覆盖、全局默认+单套覆盖、缩略图。
3. **真实渲染接入**：Remotion 渲染、Storyboard 冻结、确认门、进度、取消/重试、并发池实战。
4. **恢复与质量**：服务端重启清扫、失败重试、视频 QA（ffprobe+抽帧+音画核对）、浏览器端到端测试。

每阶段以可运行验收完成，不以「目录创建」为完成。

## 11. 验收标准（v2 增量）

- 拖拽多个房源文件夹或选择一个父文件夹，逐套正确识别；分类规则按 §3.1（含「既是房源又像父文件夹」报错）。
- 跨房源同名房间/同名文件正确隔离。
- 结构违规的套标红给出修复动作，不阻塞合规套的上传与渲染；续传按 (listing_id, rel_path, bytes) 生效。
- 并行上传（全局 4）与并发渲染（默认 2，可退 1）按预期工作；渲染中可继续上传/编辑其他套；本套编辑提示下次生效。
- 勾选多套「批量生成」入队（幂等）；未勾选保持「待确认」；排队/渲染中可取消。
- 全局默认被新套继承展示，渲染取值在生成时刻冻结。
- 刷新后状态恢复；服务端重启后渲染中作业标记失败+清扫+一键重试。
- 最终 MP4 可播放、抽帧核对画幅/运镜/片尾联系方式/房间名标签，视频不含地址或本机路径；时长符合 §5.5 公式。
- 新模块测试不依赖旧工具模块。

## 12.1 用户已拍板（不再是我的判断）

- 添加方式：**拖拽多文件夹为主 + 选择器「继续添加」**（选择器单目录，Chrome 限制）。
- 单套直选：**自动识别**——像房源→1 套；像父文件夹→拆多套；两态皆有→报错（§3.1 分类规则）。
- 取消范围：**上传和渲染都可取消**（渲染中取消=终止子进程+清理临时文件，见 §5.4）。
- 画幅：**一次一个画幅**；同一套要横+竖就生成两次，各占一个渲染任务。

## 12.2 追加钉死（来自评审 Owner Questions 的默认答案）

- 单个被添加文件夹内**混搭**（房源文件夹 + 兄弟散文件）：散文件不属于任何房源 → 黄色警告 `父文件夹根部的 3 个散图不属于任何房源，将被忽略`（父文件夹模式）；单套模式（该文件夹本身是房源）则按根散图红色阻止。
- 两个拖拽的同名根 → 后者自动加后缀 `房源A (2)` 显示名，各自独立 listing。
- 跨批次同文件夹重复上传（同名 `房源A` 两批次）：合法，创建两个独立 listing，不合并不阻止。
- 自定义音乐：单套覆盖用；上限 20 MB，格式 mp3/m4a/wav/ogg；超出给错误。
- 进度粒度：每套百分比即渲染中(x%)；队列页可展开看 `素材准备/渲染/质检` 三段（我的判断）。
- 失败重试：**人工一键重试**（渲染），上传文件级自动重试 3 次后退为人工（§3.3）。
- 一套生成时若未勾选：`生成本套` 会先自动勾选该套再入队（语义等同勾选+批量生成）。
- 全局默认继承时机：上传时快照做初始值，渲染时刻冻结取值（§5.3）。

## 12.3 补充实现约束（来自评审技术风险）

- Remotion 渲染内部 `--concurrency` 单作业帧并发默认 2（总占用 = 作业数 × 帧并发，默认 2×2）。
- SQLite：WAL + busy_timeout=5000ms，短事务；进度写入节流 ≥500ms/次。
- POST /api/listings/{id}/files 保持 stage-① 幂等语义（listing+key+size 一致跳过），批量并发安全。
- 渲染中断恢复：启动对账清扫（§5.4），不自动重排队。
- 作业心跳：worker 每 30s 写 lease；启动时渲染中但 lease 过期 → 标失败+清扫。

## 12. 默认决定（我的判断，用户可推翻）

- 渲染并发默认 2（并发尖刺不过则退 1）、上传全局并发 4。
- 多文件夹添加以**拖拽为主**、选择器单目录为辅（Chrome 无法多选目录）。
- 批次在「完成上传」时关闭；继续添加只对未关闭批次生效。
- 任务列表新在前、失败置顶可选、按状态筛选。
- 版本保留每套最近 20 个，旧版自动清理。
- 渲染中取消 = 终止子进程+清理；服务端重启不自动重排队（标失败+一键重试）。
- 续传键 (listing_id, rel_path, bytes)；同键不同内容不处理（文档化限制）。
- 进度通道用 DB+1s 轮询（SSE 后续版本）。
- 其余沿用 v1：本机单用户 Web 模块、真实浏览器上传、Python 后端 + React 前端 + Remotion 渲染（独立契约）、模块配置指定存储位置、本地合成音频（自定义音乐=用户上传自己的文件）。
